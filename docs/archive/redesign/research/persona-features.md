# Persona iOS feature inventory (source for the Android parity matrix)

> Research date: 2026-10-30. Read-only research; no repository changes.
> Sources: `docs/apple/ios.md` (entire document), `docs/assistant/assistant.md`, `docs/assistant/inbox.md`, `docs/extensions/mail.md`, `docs/apple/phone-tools.md`, `docs/apple/intents.md`, `docs/apple/live-activity.md`, `docs/server/machines.md`, `docs/integrations/terminal.md`, `docs/assistant/knowledge.md`, `docs/protocol/agent-states.md`, `docs/extensions/feishu.md`, `docs/integrations/codex.md`, `docs/operations/testing.md`, and individually checked Swift sources (each row's "Key files").
> Paths are relative to the repository root; `Persona/...` abbreviates `ios/Persona/...` by omitting `ios/`.
> Privacy: no hostnames, IPs, accounts, internal projects, real names or message content; examples use placeholders.

## 0. Scope and conventions

- **Code size**: 189 files under `ios/`, about 41,800 Swift lines (37,600 excluding tests). Targets: `Persona` (App), `Shared` (shared by App / watch / extensions), `PersonaWatch` (watchOS), `PersonaWidgets` (Live Activity Widget extension), `LiveActivity` (App Intent for Live Activity buttons), unit + UI tests. iOS 26 / watchOS 26, Swift 6 (default MainActor), only third-party dependency MarkdownUI.
- **Server contract**: the phone connects only to the hub (REST `/api/v1/...` + one WebSocket). Android should reuse these APIs; rows mark "hub changes needed" for FCM, Google login, Live Activity pushes, etc.
- **Complexity** (estimated for someone familiar with Compose): S ≤ 2 person-days; M 3–7 person-days; L ≥ 1.5 person-weeks.
- **Priority**: P0 = required for the first Android release; P1 = first batch after release; P2 = deferrable; ✕ = recommend omitting or changing form.
- **Columns**: "iOS-specific capability" identifies platform dependencies; "Android approach" lists Compose / system APIs or alternatives when no equivalent exists.

## 26. Android-only opportunities (impossible or not yet implemented on iOS)

- **Optional persistent connection**: a foreground service keeps the WebSocket alive (its notification can be the Fleet summary). `phone_*` tools are always callable, real-time state consumes no push budget, and there is no reliance on silent pushes. The cost is battery use and an ongoing notification, so make it a settings toggle (self-use distribution; the `specialUse` type is not constrained by store review).
- **Share to Persona**: from any App, share text / links / images / files to the main chat or an Agent (iOS currently has no share extension). Low cost (`ACTION_SEND` intent-filter), aligned with collecting information from everywhere.
- **More phone data**: SMS and call logs (`READ_SMS` / `READ_CALL_LOG`, no iOS API at all); `NotificationListenerService` can bring notifications from WeChat and other Apps into the Inbox. Privacy-sensitive, with separate switches; self-use distribution is not constrained by store policy.
- **Large-screen / foldable two-pane layout**: `ListDetailPaneScaffold` puts the Agents list beside the chat. A tablet and external keyboard make the terminal much better than on a phone.
- **Home-screen widgets / Quick Settings tiles**: Needs-you count, approve the first pending request.
- **Native capabilities remove workarounds**: `LazyColumn(reverseLayout = true)` natively supports reversed chat lists; `SelectionContainer` selects across paragraphs in place (iOS must open a plain-text page); lock-screen redaction has a system public version.

## 27. iOS workarounds not to port

These are SwiftUI / UIKit-specific pitfalls (see `CLAUDE.md` ("Lessons") and `docs/apple/ios.md`). On Android they either do not exist or have native solutions: safe areas, edge blur and blank screens from estimated lazy heights after flipping a ScrollView (`reverseLayout` solves this natively); SwiftUI Text cannot select across blocks; pushing a page with `.searchable` active forces the navigation bar to appear; mixing view-based and value-based `NavigationLink` inserts the new page underneath; the async `UNUserNotificationCenterDelegate` version crashes on cold start; out-of-bounds `TextField(selection:)` crashes; TextKit 2 forces line wrapping (`MonoTextView`); XCUITest switches the simulator to hardware keyboard; long modifier chains time out in Release type checking; DEBUG names collide with Swift identifiers. Conversely, these are **protocol / data-layer lessons** Android must also follow: disconnect WS in the background (otherwise `phone_*` waits); missing `has_more` means unknown; preserve backlog/live-push ordering; `client_msg_id` idempotency; canceled requests are not errors; outside ActivityKit, use Unix seconds for all times; Chinese time displays use fixed `HH:mm`.

## 28. First Android release (MVP) recommendation

**Scope = the 76 P0 items in the tables**. In one sentence: an Android phone can show Agent progress, handle decisions, process the Inbox and talk to Persona's main chat, matching iOS on the core paths.

1. Foundation: QR / manual pairing, device credentials, WS + three connection states, cache-first rendering, offline outbox, send safety, error / toast policy (sections 1 and 16).
2. Agents: project grouping (state / machine grouping uses the same sort function and is cheap enough to include), machine filtering, Needs-you cards, pins, long-press menus, close confirmation, new Agent chat (5, 6.4).
3. Chat: reversed list and entry positioning, turn-based paging, message → work-row collapse / expansion, Markdown / tools / diff / to-dos / images, pending bubbles, composer (photos / camera / shortcuts / interrupt), **four interaction panels + ScreenForm**, ⋯ menu (section 7 P0).
4. Persona tab: home, main / new / historical chats, assistant-style chat (section 2 P0).
5. Inbox: unified list, sections, waiting Agents, filters/search, swipe left to mark done, details (basic Lark conversation rendering + reply; mail detail) (9, 10.1–10.3, 12.1).
6. Push: FCM (**the only blocking hub change**), interaction buttons (allow / deny / approve / reject with input), background handling, tap routing (section 17 P0).
7. Design: one Material You light / dark theme, port state colors / tokens / components; adaptive icon (section 22 P0).
8. Engineering: debug launch arguments for direct page access + reuse `mock_hub.py` for screenshot tests (section 23 P0).

**Rationale**:

- The phone's core value is decisions and progress; P0 covers both. Reuse hub APIs unchanged; the only required server change is FCM push.
- Terminal (section 8, L complexity, the custom view most dependent on platform input and gestures) goes to P1. MVP's ScreenForm includes a View terminal snapshot + key bar fallback and handles Codex / compatible Codex forks confirmations too.
- Live Activity replacements as ongoing / Live Updates notifications go to P1: FCM already reaches users, and full Live Updates work only on Android 16 QPR1+.
- Phone tools go to P1: the assistant works without them, just without phone data; Android has no system API for the three reminder tools.
- Knowledge base, files / Git, link overlay and native Lark cards / documents go to P1–P2. During MVP, links can use Custom Tabs, and Lark cards can show a summary + Open in Lark.
- Watch, Siri, multiple themes, share cards, image editing, monitoring charts and storage go to P2 or are omitted: they do not affect the core path, and most replace platform-specific capabilities.

**First usable slice** (get it working before expanding): pairing + WS + Agents list by project + chat (rendering / send / interrupt / interaction panels) + FCM notification buttons. This tests the two biggest risks earliest: long-chat scrolling under Compose and the push pipeline.
